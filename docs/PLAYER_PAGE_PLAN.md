## 0. 一句话

**玩家要一个"壳层 + 一个全屏个人页"：页眉常驻基础信息；页眉右侧抽屉是第一个挂载点（玩法包往里放「我」）；「我」是全屏页，内部底栏是第二个挂载点（玩法包往里放背包/技能）；属性页是第三个挂载点（玩法包往里放自己的属性）。**

**关键结论**：

| # | 结论 |
|---|---|
| **1** | 三个挂载点里**只有一个需要新机制**——**壳层挂载点**（页眉抽屉）。另外两个用现成的 `ui_hook` 就能做。 |
| **2** | `ui_hook` 有一个**真实硬伤**（注入的块不再展开），正好卡住「饰品栏要在装备栏里面」。修它约 **5 行 + 一个熔断**。 |
| **3** | 「我」**不需要新机制**——它是普通视图 + 一个 `layout` 字段（约 **15 行**）。 |
| **4** | **不要**新建"视图插槽注册表"。上一轮那套（`register_view_slot` + 跨包 `<slot name>` 约定）成本高一个数量级，解决的是同一个问题。 |
| **5** | 最大的风险**不是机制不够，是契约没定**：块 `kind` 一旦被别的包 hook 就是公共契约，发布后改名 = 破坏生态。**发布前必须定死（§5 Q-3）。** |

**本轮已拍板**：

| 项 | 决定 |
|---|---|
| 抽屉归属 | **壳层**（内核自带，不随玩法包消失） |
| 「我」归属 | **玩家包的视图**，但声明"自带整个屏幕"（`layout="fullscreen"`，不画顶栏与抽屉按钮） |
| 「我」的返回按钮 | **玩家包自己在「我」界面里加**（壳层不代劳） |
| 「我」的顶栏入口 | **不加**——入口只有抽屉一条路径（Q-9） |
| 「我」里的退出登录 | **不加**——退出只从抽屉走（Q-10） |
| 全屏加载失败的兜底 | **要加**——`fullscreen` 只在组件就绪后生效，1 行（Q-6/E-6） |
| `core:info` | ✅ **保留**（Q-12）——内容作者 / 布景实体 / 内核文案继续用它 |
| 昵称 | ✅ **取代玩家化身的 `core:info.name`**（Q-4）——**昵称就是那个字段**，不是并列的第二个名字 |
| 昵称约束 | ✅ **归内核**（Q-5）——因为渲染方（内核文案 / 管理端列表 / 日志）就是内核 |
| 改名通道 | ✅ **不开特例门**（用户否决了 `set_avatar_name`）。改为 **K-7：`core:` 写入按组件声明**——`core:info` 是**数据**组件 → 可直写；`core:position` / `core:account` / `core:perception` 有**语义** → 保留动作入口 |
| **创建角色** | ✅ **搁置**（用户决定）——它是**注册后第一次进入的独立界面**；**先定"角色有什么"，最后再补创建流程**（见 §8）。因此 Q-6 / Q-11 的**机制要留、值晚定** |

## 1. 你的规划（整理）

### 1.1 页眉

| 项 | 规划 |
|---|---|
| 移除 | 「退出」等按钮**不在页眉** |
| 显示 | 基础信息，例如**当前地图名称** |
| 右侧 | 一个按钮 → **从右侧弹出抽屉** |

现状（`webui/src/App.vue:11-27`）：页眉 = `worlditor` 品牌 + 视图 tab 条 + **两个按钮**（`🗑` 永久注销 `App.vue:25`、`⎋` 退出登录 `App.vue:26`）。

### 1.2 右侧抽屉（挂载点 ①）

| 项 | 规划 |
|---|---|
| 归属 | **壳层**（内核自带） |
| 形态 | 从右侧滑出的列表 |
| 底部 | **退出登录**（壳层写死，不给玩法包） |
| 主体 | **留给玩法包扩展** |
| 玩家包在此扩展 | 一个「我」/「我的」按钮 → 进入「我」界面 |

### 1.3 「我」界面（挂载点 ②）

| 项 | 规划 |
|---|---|
| 形态 | **一个完整的界面**——**不含**默认顶栏、**不含**顶栏右侧的抽屉按钮 |
| 可扩展 | 是 |
| 底栏 | **底部横着一栏**（tab），默认只有一个按钮：**属性** |
| 默认内容 | 玩家基础信息：**id 与昵称**（id = 账户，昵称可任意写） |
| 别的包加 | 往底栏加按钮 + 对应子页（背包、技能……） |
| 返回 | **玩家包自己在界面里加** |

### 1.4 属性页（挂载点 ③）

| 项 | 规划 |
|---|---|
| 可扩展 | 是 |
| 示例 | 「武侠」玩法包加了**根骨 / 臂力 / 悟性**，属性页应当能显示 |

### 1.5 全景（本轮对齐后）

```
壳层（内核，构建时编进 bundle，不随任何玩法包消失）
 ├─ 页眉 ──── 基础信息（当前地图名…）      ← 内核读 /scene
 │     └─ 右侧按钮 → 抽屉
 │           ├─ 列表主体 = 挂载点 ① core:shell.menu  ← K-1，玩法包往里放「我」
 │           └─ 底部「退出登录」                     ← 壳层写死
 │
 └─ 主区 <main>
       ├─ 普通视图（顶栏 tab 切换）           ← register_view
       └─ fullscreen 视图「我」               ← register_view + layout="fullscreen"
             ├─ 不画顶栏 / 不画抽屉按钮（壳层决定）
             ├─ 返回按钮（玩家包自己加）
             ├─ 底栏 = 挂载点 ②（玩家包拥有）  ← 别的包用 ui_hook 加 背包/技能
             └─ 属性页 = 挂载点 ③（玩家包拥有）← 别的包用 ui_hook 加 根骨/臂力/悟性
```

### 1.6 概念对齐：视图 vs 挂载点

#### 视图（view）= 一个包提供给前端的一块 Vue 组件 + 一个 key

```
register_view(key="player", title="我", icon="🙋", provider=函数)
                     ↑              ↑        ↑          ↑
                  标识符        顶栏上显示的字  图标   返回组件文件 URL 的包函数
```

- 内核记在 `self._views`（`engine.py:1397-1402`），`GET /views` 列出来（`http.py:529-551`）
- 壳层拿到列表 → `v-for` 渲染成顶栏 tab 条（`App.vue:13-24`）
- 点 tab → `fetch` 那个 URL → `new Function` 执行 → 得到 Vue 组件 → 塞进 `<main>`（`App.vue:198-224`）

⚠️ **今天的实现里，"它是什么"和"它长在哪"是被绑死的**——`register_view` 的真实含义其实是"**给我一个顶栏 tab + `<main>` 里那块地方**"。

**这个绑定是壳层的渲染选择，不是视图概念本身。** 只要给视图加一个"我自己管整个屏幕"的声明，就能解开（见 §3 K-6）。

#### 挂载点（mount point）= 一个"别人可以往里放东西"的命名位置

四要素：

| 要素 | 含义 | 今天对应什么 |
|---|---|---|
| **名字** | 一个稳定的字符串 | `ui_hook` 的 `block_kind` |
| **归属** | 谁定义的这个位置（内核 / 某个包） | 决定"要不要新开机制" |
| **内容协议** | 往里放的东西长什么样 | `UiBlock` 列表 / 视图引用 |
| **渲染规则** | 放进去之后怎么显示、什么顺序 | 宿主决定 |

#### 统一视角：`register_view` 本身就是"往一个挂载点里放东西"

那个挂载点就是**顶栏 tab 条**（内核拥有）。于是三个位置只因为**归属不同**而处理方式不同：

| 挂载点 | 归属 | 内容协议 | 今天有吗 |
|---|---|---|---|
| **顶栏 tab 条** | 内核 | 视图引用 `{key,title,icon,url}` | ✅ 就是 `register_view` |
| **页眉抽屉列表** | 内核 | `UiBlock` 列表 | ❌ 缺 → **K-1** |
| **「我」的底栏** | **玩家包** | `UiBlock` 列表 | ✅ 用现成的 `ui_hook` 就够 |
| **「我」的属性页** | **玩家包** | `UiBlock` 列表 | ✅ 用现成的 `ui_hook` 就够 |

**内核拥有的要新开（K-1），包拥有的用现成 hooks。**

## 2. 现状核对：每一格今天能不能做

> 这一节是全部结论的地基。每条都能在代码里查。

| 层 | 你要的 | 今天 | 证据 |
|---|---|---|---|
| 页眉·信息 | 显示当前**地图名称** | 🟡 **半可以** | `/scene` 只给 `map_id`，**不给地图名**（`world/model.py:531-551`）；地图名在 `/state.maps`（`world/mcp/http.py:296`）→ 见 K-3 |
| 页眉·抽屉 | 壳层里的**可扩展列表** | ❌ **不能** | 壳层唯一的包贡献通道是 `/views` → **顶层 tab**（`App.vue:96-107`、`http.py:529-551`）；**没有"壳层挂载点"这个概念** → **K-1** |
| 抽屉→「我」 | 玩家包往抽屉加按钮 | ❌ **同上** | 抽屉不是视图；`register_view` 只能加**顶层 tab**（`engine.py:1369-1402`） |
| 「我」全屏 | 一个不含顶栏/抽屉按钮的完整界面 | 🟡 **半可以** | 视图组件能做到，但壳层今天**无条件**渲染页眉（`App.vue:11-27`）→ 需要 **K-6**（`layout` 字段，约 15 行） |
| 「我」底栏 | 别的包往底栏加 tab | ✅ **可以** | 见 §2.1 |
| 属性页 | 武侠包加根骨/臂力/悟性 | ✅ **可以** | 见 §2.2 |
| 装备栏→饰品栏 | 饰品栏在装备栏**里面** | ❌ **不能** | 见 §2.3 |

### 2.1 「我」的底栏：可以，做法是"宿主把注入的子块当 tab 渲染"

`ui_hook` 的 `block_kind` 是**自由字符串**（`engine.py:1825-1839`、`play/api.py:187-191`），没有白名单。所以：

```python
# 玩家包：产出「我」的页面树，交给内核展开
page = UiBlock(kind="worlditor_play_player:page", title="我", blocks=[
    UiBlock(kind="worlditor_play_player:attrs", title="属性", ...),   # 默认 tab
])
page = await api.apply_ui_hooks(page)      # play/api.py:193-202
return InteractionResult(text="", ui=page)
```

```python
# 背包包：往底栏加一个 tab——不需要新 API
api.register_ui_hook("worlditor_play_player:page", "after", _backpack_tab)
#   provider 返回 [UiBlock(kind="backpack:panel", title="背包", ...)]
```

宿主（玩家包自己的视图组件）拿到 `page.blocks`，**按每一项的 `title` 渲染成一个底栏 tab**。

**白拿的东西**（全部来自现有实现）：
- 世界过滤：注入方在查看者所在世界未启用 → 不注入（`engine.py:1948-1949`）
- 异常隔离：provider 抛异常 → 记日志跳过，不破坏渲染（`engine.py:1955-1962`）
- 卸载清理：`clear_play_registrations` 随包卸载回收
- 自动连线：交互结果会走同一套展开（`engine.py:3793-3794`）

**前提条件**：见 §2.3——**注入进去的 tab 自己不能再被别人扩展**。

### 2.2 属性页：可以，因为它在**原树内**

`apply_ui_hooks` 的执行顺序是**先递归展开已有子块，再应用本块钩子**（`engine.py:1941`）。

所以属性页作为玩家包**原树内的子块**，会被正常展开 → 武侠包的 `register_ui_hook("worlditor_play_player:attrs", "after", ...)` **能命中** ✅

**但这条有一个重要的反直觉点（§4 X-3）**：属性**不是内核自动列出来的**，是**每个包自己 hook 进去的**。内核的组件系统只有 key，没有中文标签/顺序/分组。

### 2.3 装备栏 → 饰品栏：不能，卡在 `engine.py:1976`

注入的块被拼进 `block.blocks` 之后，**不会再走一次展开**：

```python
# engine.py:1941  已有子块 → 展开（钩子会命中）
block.blocks = await self._expand_children(block.blocks, entity_id)
# ...
# engine.py:1976  注入的块 → 直接拼接（钩子不会命中）★ 就是这里
block.blocks = before + block.blocks + after
```

`replace` 分支（`engine.py:1971-1975`）注释里已经承认了这个不对称：

> replace：整体替换；新块的子块递归展开（**自身 replace 钩子不再应用**，防 A 的 replace 又返回 A 的循环）

**后果链**：

```
玩家包 产出 page
  ├─ attrs      ← 原树内 → 武侠包可以 hook ✅
  └─ (装备包注入 equipment)  ← 注入 → 饰品包 hook equipment ❌ 静默不触发
```

**这正是「饰品栏要在装备栏里面」的精确形态。** 而且它是**静默失败**——包作者看不到任何错误。

## 3. 缺口清单（按"最小必要"排序）

### K-1 ★ **壳层挂载点**（唯一真正的新机制）

**问题**：抽屉在壳层里，而壳层（`App.vue`）**只有 `/views` 一个包贡献通道**，且它只能加顶层 tab。

**不建议**：为新壳层再造一套 `register_chrome(...)` API（新 API = PLAY_DEV + 契约测试 + 版本门槛 + 迁移）。

**建议的最小版本**：**复用 `ui_hook`，只给壳层一块"内核保留的块 kind"**。

```python
# 内核新增一个极小的只读端点
GET /chrome  →  { "blocks": [ ... ] }
# 内核内部就是三行：
block = UiBlock(kind="core:shell.menu")
block = await engine.apply_ui_hooks(block, entity_id=viewer_id)
```

```python
# 玩家包：往抽屉里放「我」——零新 API
api.register_ui_hook("core:shell.menu", "after", _me_entry)
```

**为什么这样最省**：世界过滤 / 异常隔离 / 卸载清理 / 顺序 / 前端渲染全部沿用现成路径。

**新增面**：1 个端点 + 1 个保留 kind 命名空间 + 壳层渲染 + 文档条目。

**关键副作用（也是它最大的价值）**：**没有玩家包时，抽屉是空的，但壳层照常工作**——内核不需要知道"玩家包"存在。否则壳层就得硬编码调用 `player:me` 这个工具名，**内核硬依赖一个玩法包**，正是 D48（内置玩家包）想避免的事（详见 §4 X-2）。

### K-2 ★ **让注入的块也被展开**（约 5 行 + 熔断）

```python
# engine.py:1976 现状
block.blocks = before + block.blocks + after

# 改为
block.blocks = (
    await self._expand_children(before, entity_id)
    + block.blocks
    + await self._expand_children(after, entity_id)
)
```

**必须同时加熔断**：今天"不展开"顺带当了一道**意外的循环护栏**（A 注入 kind=A 不会无限递归）。展开之后必须有显式的环/深度限制，否则一个写错的包能把服务器递归到栈溢出。

**风险评估**：
- 这是**行为变更**（注入的块开始能被别人 hook）
- 现实风险 ≈ 0：`register_ui_hook` 目前**零真实使用者**（只在 `tests/test_engine.py`、`tests/test_world_activation.py` 里出现）
- 收益：**任意层深的跨包嵌套**，且不引入任何新 API

### K-3 页眉的数据来源

地图名有两个来源：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | `/scene` 响应补 `map_name` | `_build_scene` 里**已经取到了地图对象**（`engine.py:3678` `m = self.store.maps.get(loc.map_id)`）→ 约 2 行 |
| B | 前端把 `/scene.map_id` 和 `/state.maps` 做 join | 为了一个页眉把**全量实体**（`http.py:302-304`）拉下来，生产上不划算 |

### K-4 顺序

多个包 hook 同一个 kind → 顺序 = **注册顺序** = 包加载顺序（`play/__init__.py` 的 `_topo_order`）→ **玩家看到的 tab 顺序会随安装顺序变**。

建议：块里带 `data={"order": n}`，宿主排序，缺省按注册顺序。小改动，体验明显。

### K-5 未命中 hook 的可观测性

`register_ui_hook("player_page", ...)` 如果玩家包没装、或 kind 名写错 → **静默不触发**。

开发时无感，生产上表现为"我明明注册了，怎么不显示"。

建议：开发模式（`/meta` 带 debug 标志，或管理端）下对**未命中的 hook** 记一条警告。

### K-6 ★ **视图的布局声明 `layout`**（约 15 行）

**问题**：壳层今天**无条件**渲染页眉（`App.vue:11-27`），所以视图永远只是 `<main>` 里的一块，撑不出"不含顶栏和抽屉按钮的完整界面"。

**做法**：给视图加一个受控的布局字段。

```python
# 引擎
@dataclass
class _ViewBinding:                      # engine.py:214-221 加一行
    ...
    layout: str = "default"              # default | fullscreen

def register_view(..., layout: str = "default"):   # engine.py:1369 加参数
    if layout not in ("default", "fullscreen"):     # 受控取值，比照 :1389-1390 的 provider.type
        raise WorldError(...)
```

```python
# 包 API
api.register_view("player", title="我", icon="🙋", provider=_me, layout="fullscreen")
```

`list_views`（`engine.py:1404-1415`）多带一个字段 → `/views` 自动透传（`http.py:545-551` 原样转发）。

```vue
<!-- 壳层：两处判断 -->
<header v-if="!fullscreen"> ...顶栏 + 抽屉按钮... </header>
<nav class="view-tabs"> v-for="v in views.filter(v => v.layout !== 'fullscreen')" </nav>
```

**一个字段同时解决两件事**：不进顶栏 tab 条 + 占满全屏。

**⚠️ 安全网（必须一起做）**：`fullscreen` **只在组件成功加载之后才生效**。

```js
const fullscreen = computed(
  () => Boolean(currentView.value?.comp) && currentView.value?.meta?.layout === "fullscreen"
);
```

理由见 §4 E-6：如果「我」的组件 `fetch` 失败或执行报错，**玩家包的返回按钮也不存在**，玩家会卡在一个没有任何导航的全屏空白页里。让 `fullscreen` 依赖"组件已就绪"，壳层原有的页眉就自动成了兜底出口，**不需要新写兜底 UI**。

**顺带白拿**：`#/view/player` 是一个真实路由 → 浏览器后退键、深链接、刷新不丢（解决 §4 E-3）。

### K-7 ★ **`core:` 写入：从"命名空间一刀切"改为"组件级声明"**（约 30 行）

> **⚠️ 本节已按用户意见重写。** 原方案是"为改名开一扇受控窄门（`set_avatar_name`）"——**用户否决了它**：
> *"我不认为应该针对改名加个特例，应该是允许玩法包修改那些组件。"* **这个批评成立**，理由见下。

**问题**：Q-4 定了"昵称取代玩家化身的 `core:info.name`"，但玩法包今天写不进 `core:`（`api.py:401-421`），且 `place_entity(name=…)` 只在**创建时**能定名 → **创建之后改不了名**。

**原方案错在哪（关键事实）**：`_set_data_default`（`engine.py:3422-3436`）写一个字段做的事就是 **合并 + 存储 + 发 `on_entity_changed`**——和写任何玩法包组件**完全一样**，**没有任何不变量**。

→ **对 `core:info` 来说，根本没有东西需要保护。** 为它开一扇门，是给一个不存在的问题开特例。

**那 D46 的"三扇窄门"到底是什么？——它们不是门，是四个玩法动作**：

| 现有方法 | 它其实是**动作** | 为什么不能直写数据 |
|---|---|---|
| `set_perception`（`api.py:458`） | 让这个实体隐身 | 绕过 G12 可见性语义 |
| `move_entity` / `clear_position`（`api.py:468`） | 移动 / 下线 | 直写字段**不发 `on_entity_move` / `on_entity_enter`**（`engine.py:3272-3273`；`_set_data_default` 只发 `on_entity_changed`，`:3434-3436`）→ **订阅移动的包全漏掉** |
| `claim_avatar` / `release_avatar`（`api.py:628` / `:650`） | 认领 / 退掉化身（D46 两本账） | 可把**任意实体绑到任意账户** → 绕过 D14 保护与 roster 一致性 |

**它们不是"写某个字段的特例"，是四个语义操作。而"改名"不是动作，就是写数据** →
**判定标准应该是"有没有语义"，不是"在不在 `core:` 命名空间"。**

**建议形状**：让组件声明自己。

```python
CORE_COMPONENTS = {
    "core:info":       CoreComponent(writable=True,  validate=_check_display_name),
    "core:position":   CoreComponent(writable=False, use="move_entity / clear_position"),
    "core:account":    CoreComponent(writable=False, use="claim_avatar / release_avatar"),
    "core:perception": CoreComponent(writable=False, use="set_perception"),
}
```

**两个好处**：

1. **加新 `core:` 组件时顺手声明**，不用改守卫逻辑
2. **报错能说人话**：今天拒绝时报的是"core: 是内核保留的组件命名空间，玩法包不得写入"（`api.py:412-414`）——**没告诉作者该走哪条路**。改成"`core:position` 不能直写，请用 `move_entity` / `clear_position`"

**顺带收口 Q-5**：长度 / 控制字符 / 双向文本的校验挂到 `validate` 上——**校验也不是特例，是组件声明的一部分**。改名冷却仍归玩家包。

**⚠️ 这不是"操作级特例"**：用户反对的是"为**改名**开一个 `set_avatar_name`"（操作级）；这里是"**`core:info` 是数据组件，所以可写**"（组件级分类）。两者不是一回事。

**要确认的范围**：默认放开（fail-open：忘声明 = 漏一个后门）还是默认拦截（fail-closed：忘声明 = 少一个能力）？**建议 fail-closed**——守卫的意义就是防"忘了"；而内核 `core:` 组件屈指可数（4 个），新增要改内核代码 + 文档，漏声明的概率低。

**K-7 落地后，Q-4 的执行方式变成最简单的一种**——玩家包直接写字段：

```python
await api.set_data(avatar_id, "name", nickname, component="core:info")
```

**不需要新 API、不需要新概念。** 而 `/scene` 的 peers 与 `/state` 的 entities **天然带上新名字**（`entity.to_dict()` 直接透传 `components`，`http.py:370-394`）→ **世界里的其他玩家自动看到昵称**，不需要批量解析、不需要渲染层覆盖、不需要改前端。

### 5.1 逐条展开（未定项）

#### Q-12 ✅ 已定：**保留 `core:info`**

> **✅ 决定（本轮）**：`core:info` **保留**。内容作者 / 布景实体 / 内核文案继续用它；"玩法不进内核"的诉求改由 **Q-4 在字段语义上解决**（昵称取代玩家化身的显示名）。

以下为决策档案（保留理由与代价的推演过程）。

**用户立场**：`core:info` **不应该存在**——内核不应该有"实体名/描述"这个组件；**内核没有玩家可见的视图**。

**事实**：它确实存在（`model.py:48` `CORE_INFO = "core:info"`），而且是一个**有记录的决定**——DESIGN **D40**：

> `core:info` **保留**，但理由从"供渲染"变为"**内核自己的文案**"（lint / 删除保护 / 日志）；客户端要不要用它兜底显示是玩法包的事

所以用户的立场**比 D40 又往前走了一步**：不是"改理由保留"，而是"**连这个理由也不成立**"。

**支持删除的最强论据（来自代码本身）**：

`Entity.name` **缺失时兜底为 `id` 前 8 位**（`model.py:746`），`desc` 兜底为空串（`:757`）。
→ **兜底存在，说明 `core:info` 不是协议，只是便利。** 内核在它缺失时照常工作。

**删除的真实代价——它撞在 G35 / D40 上**：

管理端今天能列出实体名，**唯一原因是它是内核保留组件、键是已知的**。把名字移进玩法包组件后，管理端要显示它就需要**组件渲染器**——而 D40 明确拒绝做（"不做组件声明端点、不做组件渲染器"）。

于是逼出一个新问题：**管理端的实体列表显示什么？**

| 选项 | 评价 |
|---|---|
| (a) 就显示 id | 诚实，但**内容作者没法用** |
| (b) 破例留一个"作者标签" | 那它还是 `core:info`，只是换了理由 |
| (c) 实体列表也交给包（管理端**有** `register_admin_page`） | 一致，但要有人写那个页面 |

**顺带一个真问题**：删掉之后，**"实体叫什么"归谁？** 特别是**布景实体**（商贩、告示牌、一只野狼）——那是**内容作者**在编辑器里填的，不是玩法逻辑。

**成本面**：

| 面 | 说明 |
|---|---|

**对 Q-4 的直接影响**：删掉之后，Q-4 的**选项 A（昵称 = 化身名）从"白拿内核的"变成"玩家包自己定义一个"**——成本从 0 变成一次设计。

**建议**：**这是内核级决策，不要塞进玩家包这一版。** 它应该先独立拍板（并且要真的改 D40 的正文），否则玩家包会建在一个正在被拆的地基上。

#### Q-4 ✅ 已定：**昵称取代玩家化身的 `core:info.name`**

> **✅ 决定（本轮）**：玩家包的**昵称取代玩家化身的 `core:info.name`**——**昵称就是那个字段**，不是并列的第二个名字。
> **推论**：昵称是**化身级**的（一具化身一个）；账户那边只剩 `id`（= `accounts.username`，登录名）。
> **前置条件**：需要新的受控窄门 **K-7**（今天玩法包创建后改不了名）。
> **约束归属**：长度 / 控制字符 / 双向文本 → **内核**（K-7 窄门里做）；改名冷却 → **玩家包**。

以下为决策档案（推演过程）。


**用户原话**：属性页显示 **id 与昵称**（id = 账户，昵称可以任意写）。

**但今天系统里已经有两个"名字"，而且都不符合"可以任意写"**：

| 名字 | 存哪 | 约束 | 谁能看到 |
|---|---|---|---|
| **账户名** `username` | `accounts` 表，**UNIQUE**（`store.py:177`） | **2–24 字符，只允许字母数字 + `_` + `-`**（`identity.py:466-472`） | **登录凭据** |
| **化身名** | `core:info` 组件的 `name`（`model.py:658-659`） | **内核无统一校验**；缺失时兜底为 id 前 8 位 | **世界里的其他玩家**（`/scene` 的 peers 走 `entity.to_dict()` → `components["core:info"]`，`http.py:370-394`） |

**冲突点**：
1. `username` **就是登录名**（`identity.py:230` `get_account_by_username` 用它查账户）→ **改它等于改账号**，不可能"任意写"
2. 而 `Principal` 的注释却说它是**显示名**（`model.py:1012`）—— **两种语义压在同一个字段上**
3. **今天没有任何改名接口**（全仓库只有 `rename_folder`，那是编辑器文件夹的，`engine.py:2802`）

> 补充事实：`_check_username` 用的是 `str.isalnum()`，而 **Python 的 `isalnum()` 对中文返回 True** → 所以「张三」这类**中文名今天是合法的**，被挡掉的是空格、标点、emoji。

**所以"昵称"只能三选一**：

| 选项 | 是什么 | 代价 |
|---|---|---|
| **A. 昵称 = 化身名** | 复用 `core:info.name` | 一个账户多具化身 → 多个昵称；且**它是世界可见的**（`/scene` 的 peers 直接透传 `components`）。⚠️ **依赖 Q-12**：若 `core:info` 被删，此选项从"白拿内核的"变成"玩家包自己定义一个" |
| **B. 昵称 = 新的账户级显示名** | 与登录名解耦，另起一个 | 要定存哪（玩家包 KV？内核账户表加列？），以及**改了之后世界看到的名字变不变** |
| **C. 两个都要** | 账户级昵称（自己看）+ 化身名（世界看） | 最灵活，但要向玩家解释"为什么我改了昵称别人看到的没变" |

**为什么这是地基（不只是命名问题）**：属性页要显示"id 与昵称"，而 `id` 是**账户**、`昵称` 若也是账户级，那**这个页面里根本没有化身的位置**——可玩家在世界里是用化身行动的。**「我」这个页面到底在讲"账户"还是"化身"，必须现在回答。**

**建议：C，但属性页显式分成两段**——「账户」（id + 昵称）与「当前角色」（化身名 + 化身数据）。因为 D45 之后**主体 ≠ 实体**是这个项目自己的第一性事实。

#### Q-5 昵称的约束——归谁，由"谁渲染它"决定

| 昵称出现在哪 | 校验归谁 |
|---|---|
| 只在「我」里（自己看） | **玩家包自己说了算**，内核不该管（D31/D48 的一贯结论：玩法规则归玩法包） |
| 世界里的 peers 列表 / 聊天 / 排行榜 | **渲染方**必须能处理任意内容（截断、转义、过滤） |
| 进内核的展示面（如 `/scene`） | **内核必须校验**——今天 `entity.name` 没有统一校验 |

**约束清单（按危害排序）**：

| # | 项 | 说明 |
|---|---|---|
| 1 | **双向文本覆盖符**（U+202E 等） | 最狠：能让显示名**整个反过来**，冒充别人。连"长得像"都不需要，是直接改显示顺序 |
| 2 | **零宽字符 / 同形字** | 冒充 |
| 3 | **长度** | 顶栏 tab、抽屉列表、peers 列表都会显示名字。沿用 `_check_username` 的 2–24 口径即可 |
| 4 | **重名** | 账户名 UNIQUE 天然不重；**化身名可以重**——世界里两个「张三」技术上完全合法，今天没有任何机制区分。**要区分就永远用 id**，显示层可加后缀（`张三#a1b2`） |
| 5 | **改名冷却** | 无限制 = 改名逃避举报 |

#### Q-3 块 kind 的公共契约——**不是决策，只是文档义务**

> **✅ 结论：不需要决策。** 玩法包往玩家包的界面里加东西，就依赖玩家包的命名——**改名会破是架构的必然，理所当然，不需要"解决"**。插件依赖宿主命名，天经地义。要做的事只有一件：**写进 `PLAY_DEV.md`**，让别人查得到。

**命名**：仓库已有命名空间规则（D33/D43：`core:` / `<play_id>:` / `local:`），组件键就是 `source:name`（`model.py:933-941`）。**块 kind 沿用同一套即可**：内核保留 `core:`（如 `core:shell.menu`），包用 `<play_id>:`（如 `worlditor_play_player:page`）。这不是新决策，是套用已有决策。

**真正缺的是 `PLAY_DEV.md` 里的一张表**，每个挂载点要写清四样：

| 要写什么 | 例 |
|---|---|
| kind 字符串 | `worlditor_play_player:page` |
| 语义 | 「我」界面的底栏 |
| **内容协议** | **注入的块必须长什么样** |
| 稳定性承诺 | 改名 = breaking change |

**第三样最容易被漏**——「我」的底栏 / 抽屉条目靠三个**约定字段**渲染，三个都不是内核强制的：

```python
UiBlock(
    kind="backpack:panel",
    title="背包",               # ← tab 上显示的字（约定）
    icon="🎒",                  # ← 图标（K-8 已落地，v0.9.0）
    data={"view": "backpack"},  # ← 点它去哪（宿主认识的字段，**不是 action**）
    items=[...],                # ← 子页内容
)
```

**不写进文档，包作者只能靠猜，猜错了还没有报错。** 尤其是"点击去哪"——`UiBlock.action` 至今**没有执行者**（渲染器只 `emit`，壳层无人消费），所以导航必须走 `data` 里的宿主约定字段。

**可发现性（新子项）**：包作者怎么知道有哪些挂载点？今天只有读文档，且**写错了静默失败**。
- 被动发现 = **K-5**（开发模式警告未命中的 hook）→ **推荐先做这个**
- 主动发现 = 一个"挂载点清单"出口（新 API）→ 倾向先不做

**为什么要现在定**：kind 一旦有包 hook 上去，改名就是破坏生态。**发布前定死成本为零。**

#### Q-2 顶栏 vs 底栏——**不是决策，玩法包自己选**

> **✅ 结论：这不需要你拍板。** 两种写法（`register_view` / `ui_hook`）都开着，**包作者自己选**——这也是唯一正确的答案。桌面软件里"扩展把 UI 放哪"同样是厂商自己定，生态自己收敛。
>
> **我上一轮把它升格成"必须先有规则"是过度治理**：平台今天有 **0 个第三方玩法包**，为一个还不存在的生态立法，和之前那套"视图插槽注册表"是同一个毛病——**为想象中的需求设计**。
>
> 保留下来的是**两样不是规则的东西**：①**技术事实**——顶栏 `overflow-x: auto`，手机上 4–5 个 tab 就横滑；②一句**建议默认**（写进 `PLAY_DEV.md`，明确标"建议，不强制"）。

顶栏是 `overflow-x: auto`（`styles.css:62-73`）→ **手机上超过 4–5 个 tab 就要横滑**；「我」的底栏同理。

所以规则不能只回答"二选一放哪"，必须回答**放不下的去哪**：

| 层 | 合理容量 | 放什么 |
|---|---|---|
| 顶栏 tab 条 | **3–5** | **看世界**：场景 / 地图 / 日志 / 聊天 |
| 「我」底栏 | **4–6** | **看我**：属性 / 背包 / 技能 / 装备 |
| 子页内部 | 不限 | **具体分类**：背包分页、技能流派 —— **靠 K-2 的嵌套** |

**建议写进 `PLAY_DEV.md` 的四条**：
1. 顶栏只放"与地点/世界相关、需要随时切换"的
2. 「我」底栏放"关于我这具化身 / 这个账户"的
3. 再细的往子页里嵌（K-2）
4. **同一个功能只允许一个入口**——防生态长歪的关键一条

**不定的后果**：同一个背包包在不同世界可能出现在不同位置（D15 世界过滤会让视图在某些世界不显示），玩家找不到功能；包作者互相抄，抄出不一致。

## 8. 角色有什么（数据模型现状）

> **背景**：用户决定**先搁置创建角色**——"因为不知道创建一个角色需要哪些，所以先关注角色有什么，最后再加创建流程；创建角色应该是第一次注册进入后有个单独的界面"。本节就是"角色有什么"的现状核对。

### 8.1 今天的内核答案：实体 = `id` + `components`

角色有什么 = **它带了哪些组件**（D41：能力 = 组件的存在）。

**内核保留的 4 个（协议数据，不算能力——`capabilities()` 里被显式跳过，`engine.py:1049-1050`）**：

| 组件 | 有什么 | 谁能写 |
|---|---|---|
| `core:info` | `{name, desc}` | **包可直写**（K-7 之后）；缺失兜底 `id` 前 8 位 |
| `core:account` | `{user_id}` | 只能走 `claim_avatar` / `release_avatar` |
| `core:position` | `{map_id, row, col}` | 只能走 `move_entity` / `clear_position` |
| `core:perception` | 隐身相关 | 只能走 `set_perception` |

**其余全部是包的组件**，三种来源：`<play_id>:<name>`（自己的）、`local:<name>`（共享/内容）、虚构（无声明）。

### 8.2 ★ 关键发现：属性页**不需要** `ui_hook`——内核已有整套声明设施

**`api.declare_component(name, label=..., fields=[...])`**（`api.py:39-56`、`engine.py:724-769`）：

```python
api.declare_component(
    "attributes",
    label="武侠属性",                                  # 组件的中文名
    fields=[
        {"name": "gen_gu", "label": "根骨", "type": "int", "default": 10},
        {"name": "bi_li",  "label": "臂力", "type": "int"},
        {"name": "wu_xing","label": "悟性", "type": "int"},
    ],
)
# → wuxia:attributes，带**中文标签**的字段 schema（字段形态 {name, label, type, default?}）
```

**`api.capabilities(entity)`**（`api.py:145`、`engine.py:1028-1061`）已经汇总：

```python
{
  "components": [...],
  "active_components": [...],      # 生效
  "inactive_components": [...],    # 声明在，但该世界未启用
  "orphan_components": [...],      # 声明它的包没加载
  "fictional_components": [...],   # local: 且无声明（虚构）
  "interactions": [...],           # 动作并集
  "fields": {"wuxia:attributes": [{"name": "gen_gu", "label": "根骨", "type": "int"}]},
}
```

**`fields` 就是"按组件分组、带中文标签"的属性清单**——属性页要的东西，内核已经在给了。

### 8.3 所以属性页有两条路，**应该组合**

| 路 | 做法 | 谁做 | 包的成本 |
|---|---|---|---|
| **甲：自动** | 玩家包读 `capabilities(entity)["fields"]` + `get_component(entity, key)` 取值 → 渲染成按组件分组、带中文标签的表 | **玩家包** ✅ 不违反 D40 | **零**——包只要正常 `declare_component` 就自动出现 |
| **乙：定制** | `ui_hook("worlditor_play_player:attrs", "after", …)` 注入自定义行（进度条 / 装备加成 / 图标） | 各包 | 每包都要写 |

**甲是默认，乙是例外。**

D40 只禁止**内核**做组件渲染器（"不做组件声明端点 / 不做组件渲染器"）——**玩家包做这件事完全合规**：数据是内核给的，呈现是玩法给的。

### 8.4 这条发现改变了什么

1. **Q-3 的内容协议变轻**：属性页的 hook 从"必须"降级为"**可选覆盖**"
2. **武侠包的例子被直接满足**：`declare_component` 带 `label` + `fields` → 属性页自动显示根骨 / 臂力 / 悟性，**一行 hook 都不用写**
3. **四象限白送**：武侠包在某世界没启用，它的属性**自动不出现**（`inactive_components`），编辑器还能解释"为什么没效果"

### 8.5 ⏳ 待定：属性该是"一包一组件"还是"共享组件"

| | 形态 | 优点 | 缺点 |
|---|---|---|---|
| **A. 一包一组件**（倾向） | `wuxia:attributes`、`equip:bonus` 各是各的 | 边界清楚（D43 天然满足）；属性页按组件分组，**天然不打架**；四象限按 source 分桶一目了然 | 包之间读不到对方属性（要 `call_service`）；一个角色可能有多个属性组件 |
| **B. 共享组件 + `add_tag_fields`** | 一个 `local:attributes`，武侠包往里追加根骨 | 所有属性在一个组件里，跨包读取容易 | `local:` 谁都能加（靠"留痕"）；**同名字段重复声明会报错** |

**倾向 A**：`capabilities.fields` 本来就是按组件分组的（DESIGN.md:264），A 是顺着设计走；B 的唯一优势（跨包读属性）可以用 `call_service` / 事件解决。

### 8.6 ⏳ 还没设计：玩家包自己的组件

按 A 的形态，"角色有什么"的完整清单是：

- 内核 4 个协议组件（已定）
- **玩家包自己的组件** ← **这一格是空的，需要设计**
- 其他玩法包（武侠 / 装备 / 背包…）

**建议先列空位、不填内容**——因为创建角色已搁置，而"创建时要填什么"正是这套组件的投影。

### P1 ★ `UiBlock` 没有图标字段

`UiBlock` 的字段是 `kind / title / text / fields / items / actions / data / blocks`（`model.py:985-992`）——**没有 `icon`**。

而视图登记有 `icon`（`_ViewBinding`，`engine.py:220`）。

**后果**：抽屉里注入的「我」条目、底栏 tab，**都没有地方放图标**。要么塞进 `data`（需要约定），要么给 `UiBlock` 加一个 `icon` 字段。

→ 这是**内容协议层**的硬缺口，直接关系到 Q-3 那张契约表。

### P2 `/chrome` 的认证档位没定

`/views` 是**免认证**的（"元数据无敏感信息"，`http.py:530-532`）。

但 `/chrome` 会**执行玩法包代码**（`apply_ui_hooks` 调 providers），返回的可能是有权限内容 → **不能免认证**。

要定：read 档（围观）能不能看抽屉？admin 档呢？

### P3 管理端的 `layout` 怎么处理

管理端也用同一个加载器预览视图（`pages/admin/PlayPageHost.vue:88-93`），但管理端是 **PC 全宽布局**。`layout="fullscreen"` 在那里生效会把布局搞乱。

**建议：`layout` 只在玩家端生效**（`App.vue`），管理端忽略。要明确写下来，否则实现时容易顺手抄过去（两份加载器，见 X-5）。

### P4 ⚠️ 玩家所在世界变了，壳层不会刷新

壳层只在 **`plays_changed`** 时重拉 `/views`（`App.vue:155-170`）。

但"玩家在哪个世界"由 `core:position.map_id` → `store.map_world` 决定（`engine.py:2076-2079`、`:2557-2559`），它变化时：

- 玩家**跨世界移动** → 只发 `on_entity_move` / `on_entity_enter`
- 管理员**把地图改归属世界**（`update_map(world_id=…)`）→ 只发 `on_world_edited`

**壳层两个都不监听** → 顶栏 tab、抽屉、页眉信息**全部陈旧**。

**是否真会发生**：跨世界移动需要世界作者把路径连到另一个世界的地图；管理员改归属更直接。**不是高频，但一旦发生就是"看到不该看的 tab / 少看到该看的 tab"**，且玩家自己无法修复（只能刷新页面）。

**建议**：壳层监听 `on_entity_move` / `on_entity_enter`，**map_id 变了才重拉** `/views` + `/chrome` + 页眉。这条和 E-5 是同一件事的两半。

### P5 世界激活判定的重复验证——用户方向：**让世界隔离更彻底**

**现象**：`_apply_ui_hooks_locked` 对**每个块的每个钩子**都调一次 `play_active_for_entity`（`engine.py:1948`），它要查 实体 → 地图 → 世界 三级（`:2107` → `:2076-2079`）。同样的判定还出现在工具过滤、`/views` 过滤、interaction 分派、`_live_components`。抽屉每开一次展开一次块树；「我」每进一次展开一次。

**✅ 用户方向（本轮）**："考虑减少反复验证玩法包是否在当前世界启用，例如让世界间的隔离更彻底一些。"

**性能核算（先说清量级，免得为微秒付大代价）**：一个 40 块的树、每块平均 2 个钩子 = 80 次判断；每次 3 次内存字典查表 → **240 次哈希查找，微秒级**。**真正会慢的是 provider 本身**（async、可能有 IO）。

#### 三种读法

| 读法 | 做法 | 大小 | 风险 |
|---|---|---|---|
| **甲：一次解析、多处复用** | 展开时在顶层解析出 `world_id`（或直接算出"生效包集合"），逐层传下去；每处判断退化成一次集合查找 | **约 10–20 行** | **零语义变化** |
| **乙：每个世界一份运行时快照** | 维护 `{world_id: frozenset[play_id]}`，过滤只读快照 | 约 60–100 行 | ⚠️ **缓存失效负担**：世界 `play_ids` 变更、包启用/禁用/加载失败都要刷新。**今天"每次现算"虽然重复，但永远不会过期** |
| **丙：收紧默认语义** | 今天"世界不存在 / `play_ids` 空 / 世界未知"**三处都默认放行**，改成显式 | 小 | 破坏性变更 |

**建议：做甲，不做乙。** 乙省下的是微秒，付出的是正确性负担——不划算。

#### ⚠️ 但"隔离更彻底"的实质问题在丙：今天有**三处默认放行**

`_world_play_active`（`engine.py:2081-2093`）+ `play_active_for_entity`（`:2076-2079`）：

| # | 情况 | 今天 | 松在哪 |
|---|---|---|---|
| 1 | 实体**不在世界上**（`map_id=None`，下线 / 收进容器） | **放行**（`:2077-2078`） | "不在世界上"被当成"不设限"——D36 说这是**合法常态**，但它不等于"没有规则" |
| 2 | 地图未归属世界 | 落到**默认世界**（`:2095-2099`） | 合理（"没有归属"≠"没有规则"），保留 |
| 3 | **`play_ids` 为空** | **全部激活**（`:2091-2092`） | **把"空"当成"全"**——和 D36 在 `core:position` 上定的"缺失要显式、不兜底"原则**不一致** |

**最值得改的是 ③**：用"空数组"表达"全部启用"，正是"把缺失当语义"的坑。建议改成**显式两种状态**（例如 `play_ids` 空 = 世界没有任何包；要"全部"就显式标记）。

**但它是破坏性变更，而且有一个真实的产品悬崖**：今天新建世界 `play_ids` 是空的 = 什么都能看见；改成"空 = 没有包"之后，**新建世界默认什么都看不见**（G39 残留 #4 那类空界面）。要配套解决"新世界的默认启用集合"，否则是把一个宽松默认换成另一个坑。

**所以丙不该和玩家包一起做**，它是独立的语义收紧项目（和 K-9 同类：独立、可单独提交）。

#### 丙到底说什么：让"世界的启用集合"从**两态**变成**三态**

**今天的实际行为**（`engine.py:2091-2093`）：

```python
world = self.store.worlds.get(world_id)
if world is None or not world.play_ids:
    return True                    # ← 空数组 = 全部启用
return play_id in world.play_ids   # ← 否则按名字匹配
```

| 管理员想要 | 今天的写法 | 结果 |
|---|---|---|
| 这个世界启用**全部** | `play_ids = []` | ✅ 全部 |
| 这个世界启用**这几个** | `play_ids = ["wuxia", "equip"]` | ✅ 这几个 |
| 这个世界**什么都不启用** | **没有写法** | ❌ 做不到 |

**两条**：

1. **两个不同的意图共用一个值**——「我还没配置过」和「我要全部」都是 `[]`，区分不开。
2. **"这个世界不启用任何包"无法表达**。唯一绕法是塞一个不存在的包名（`play_ids = ["__none__"]`），靠 `in` 判断碰巧为 False——**这是靠副作用实现的**，没人会想到，也没有任何地方会这么写。

**丙 = 把"全部"变成显式状态**，于是三态各自可表达：

| 方案 | 形态 | 评价 |
|---|---|---|
| (a) `play_ids: list \| None` | `None` = 全部，`[]` = 没有 | 简单，但又是"用缺失表达语义"，和 D36 精神打架 |
| (b) 加 `plays_mode: "all" \| "selected" \| "none"` | 显式三态 | ✅ 最清楚，但要动数据模型 |
| (c) 哨兵值 `play_ids = ["*"]` | 魔法字符串 | 不改表结构，但"魔法值" |

**关键约束：默认值必须仍然是"全部"。** 否则全新安装的世界什么都看不见——把 G39 残留 #4 那个空界面问题重新引爆，把自举路径砍掉。

**代价**：破坏性变更（现存世界的 `[]` 会从"全部"翻成"没有"）。项目规定 D13 **无迁移、删库重建**，所以技术上可接受，但管理端要有重新配置的入口。

#### 顺带一个相邻问题：**"启用了一个没装的包"是盲区**

若 `play_ids = ["wuxia"]` 而 wuxia **没有加载**：
- `play_active_for_entity(e, "wuxia")` → **True**（名字在集合里）
- 其他所有包 → **False**
- → 这个世界的视图、工具**全部消失**

而**没有任何诊断**告诉你"你的世界被配置指向一个不存在的包"。

**对比**：组件那边有**四象限诊断**（D44：`active` / `inactive` / `orphan` / `fictional`），孤儿组件一目了然。**"世界的启用集合"没有对应的诊断**——这是个真实的对称性缺失。

#### 丙的诚实优先级

**这是 latent 债务，不是现在的 bug。** 今天没有受害者：没有任何世界需要"不启用任何包"，也没有人因为 `[]` 的歧义出过错。

所以丙**不该排在玩家包前面**，它跟 K-9 一样属于"顺手清理"级别的独立项目。**先做甲就够了。**
