## 0. 一句话

**玩家要一个"壳层 + 一个全屏个人页"：页眉常驻基础信息；页眉右侧抽屉是第一个挂载点
（玩法包往里放「我」）；「我」是全屏页，内部底栏是第二个挂载点（玩法包往里放背包/技能）；
属性页是第三个挂载点（玩法包往里放自己的属性）。**

**关键结论（现状版）**：

| # | 结论 |
|---|---|
| 1 | 三个挂载点里**只有壳层挂载点需要新机制**——它已经做完了（K-1 / D52）。另外两个用现成的 `ui_hook`。 |
| 2 | **今天没有任何机制缺口挡住玩家包**。剩下的全是"写包"和三个小残留。 |
| 3 | ★ **最大的风险已经不是机制，是"没有玩家包"**——空安装时玩家端仍然只有空态，`/views` 为空（G39 残留 #4）。 |

### 1.6 概念对齐：视图 vs 挂载点

**视图（view）** = 一个包提供的前端组件 + 一个 key。

```python
register_view("player", title="我", icon="🙋", provider=..., layout="fullscreen")
```

内核记在引擎里（`engine.py:1392`），`GET /views` 列出来（`http.py:520`），壳层按 `layout`
分流：`default` 进顶栏 tab，`fullscreen` 不进 tab、占满 `<main>` 并隐藏页眉。

**挂载点（mount point）** = 一个"别人可以往里放东西"的命名位置，四要素：
名字（块 kind）、归属（内核 / 某个包）、内容协议（`UiBlock` 列表 / 视图引用）、渲染规则。

| 挂载点 | 归属 | 内容协议 | 现状 |
|---|---|---|---|
| 顶栏 tab 条 | 内核 | 视图引用 `{key,title,icon,url,layout}` | ✅ `register_view` |
| 页眉抽屉列表 | 内核 | `UiBlock` 列表 | ✅ **K-1 / D52** |
| 「我」的底栏 | **玩家包** | `UiBlock` 列表 | ✅ 机制够（`ui_hook`），包未写 |
| 「我」的属性页 | **玩家包** | `UiBlock` 列表 / 自动渲染 | ✅ 同上；**默认走自动渲染**（§10.2） |

### 3.1 K-2 的语义比原计划更保守（重要）

原计划只写"加一个深度熔断"。**实际实现多了一层"钩子身份去重"**：

- `spent` = 沿当前展开路径**已经应用过的 `(块 kind, 位置, play_id)` 集合**（`engine.py:2002` 起）
- 同一个钩子在**同一条路径**上最多应用一次
- 深度上限 `_UI_HOOK_MAX_DEPTH = 32`（`engine.py:334`）仍保留，作兜底

**为什么必须这样**：`spent` 只挡"同一条路径重复命中"，**不挡合法的同 kind 嵌套**（原树的
子块共享同一个 `spent`、不新增条目）。所以：

- ✅ 装备包注入装备栏 → 饰品包 hook 装备栏 → **可以**（K-2 的初衷）
- ❌ A 的 `after` 钩子返回一个同 kind 的块 → **不会无限递归**

⚠️ **这是行为变更**：注入进去的块**不再是叶子**。v0.9.0 之前"注入块不展开"顺带当了一道
意外的护栏，现在护栏是显式的。

### 3.2 K-3 最后没走 `/scene`，走了 `/where`

| | 原计划 | 实际 |
|---|---|---|
| 做法 | `_build_scene` 补 `map_name`（约 2 行） | 新开 `GET /where` |

**为什么改了**：页眉要的是**世界 + 地图**两个名字（原计划只想了地图），而 `/scene` 是

"装饰信息"不同。**`/where` 更小、更专用、失败也不影响主区**（`App.vue:212` 只 `console.warn`）。

### 3.5 K-11 显示名校验（v0.9.1 补上的那一笔）

**背景**：K-7 让 `core:info` 可直写（否则玩家包改不了名），但 Q-5 定的
"长度 / 控制字符 / 双向文本归内核"一直没实现——文档却写着"已定"。补上了。

**规则**（`model.check_display_name`，只做四件事）：

| 做什么 | 细节 |
|---|---|
| 去首尾空白 | `"  张三  "` → `"张三"` |
| 拒空 | 全空白 / 非字符串 → 报错 |
| 限长 | `DISPLAY_NAME_MAX = 24` 个**字符**（中文按 1 计） |
| 拒"会改变显示效果"的字符 | Unicode 类别 `Cc`（换行/制表等）、`Cf`（**双向控制符** `U+202A–202E` / `U+2066–2069`、**零宽** `U+200B–200D` / `U+FEFF`）、`Zl` / `Zp`（行段分隔符） |

**唯一放行的 `Cf` 是 ZWJ**（`U+200D`）——否则 👨‍👩‍👧 / 👩‍💻 这类 emoji 序列全废。代价已记录：
ZWJ 仍可用于"零宽冒充"，但同形字（西里尔 `а` 冒充拉丁 `a`）内核本来也挡不住，
挡一个不挡另一个是安全剧场（D49 的原话：内核"只保证不污染内核文案，不保证名字是真的"）。

**六个写入出入口全部接上**（这是 K-11 的核心，少一处就等于没做）：

| # | 入口 | 落点 |
|---|---|---|
| ① | 字段写 `set_data` | `_set_data_default` → `validate_core_field` |
| ② | 同上，**玩法包那条门** | 同一条路径（`core:` 跳过玩法包原语表，D33 → 包绕不过去） |
| ③ | 整块写 `set_component` | `_set_component_default` → `validate_core_payload` |
| ④ | 建组件 `add_component` | `_add_component_default` → 同上 |
| ⑤ | 管理端 `update_entity` | `name=` 与 `components=` **两个入口都校验** |
| ⑥ | 创建 `place_entity` / `import_bundle` | `_compose_entity` → 显式 `name` 走校验 |

**两条刻意的边界**：

1. **`desc` 不校验**——描述本来就是多行长文本
2. **组件 `label` 派生的名字不校验**——那是**作者数据**，不是玩家输入；否则一个起了长
   label 的包会让 `place_entity(kind=…)` 突然全失败，而报错指向的地方跟它无关

**不做**：同形字 confusables 表（成本 >> 收益）、重名检查（Q-5 已定用 id 区分）、
NFKC 归一（会改写用户输入）。**冷却仍在玩家包**（那是玩法规则）。

**回归**：`tests/test_display_name.py`（19 条：规则本身 + 六个入口 + 两条边界 + 中文/emoji 放行）。

### 10.2 ★ 属性页不需要 `ui_hook`——内核已有整套声明设施

```python
api.declare_component(                      # api.py:39 → engine.py:747
    "attributes", label="武侠属性",
```

`api.capabilities(entity)`（`api.py:145` → `engine.py:1051`）已经汇总出

属性页要的东西，内核已经在给了。

|---|---|---|---|
| **甲：自动（默认）** | 玩家包读 `capabilities(entity)["fields"]` + `get_component` 取值 → 渲染按组件分组、带标签的表 | 玩家包 ✅ 不违反 D40 | **零**——包正常 `declare_component` 就自动出现 |

## 11. 进场流程（Q-11：首次创建 / 后续上线）

**你给的定义**：

| 时机 | 走什么 |
|---|---|
| **第一次**（还没有化身） | 注册 / 创建角色的流程（独立界面） |
| **之后**（有化身） | **上线界面**：二选一 —— ①**回到下线前位置** ②**候选的出生点** |

**机制**：仍然需要 **K-10**（视图可声明"默认落地"），但它落地的是**流程入口视图**——
流程内部再按状态分支，**壳层不需要知道**"创建"和"上线"是两件事，更不需要知道玩家有没有
化身（否则内核又开始管玩法，K-1 的红线）。

```
壳层：无路由 → 落到 landing 视图（K-10）
   └─ 玩家包的进场视图（fullscreen）
        ├─ player_whoami → 没有化身？      → 创建角色界面
        └─ 有化身、但不在世界上？          → 上线界面（二选一）
              ├─ 回到下线前位置
              └─ 候选出生点
```

### 11.1 三个必须先回答的技术问题（不然实现时会卡住）

**① "下线前位置"存哪？**

今天**没有任何内核代码会自动清位置**——`clear_position` 只有包会调（`api.py:475`）。
也就是说"下线"在数据上**根本没发生**：实体还站在原地。

→ 两个选项，**必须写下来，不能默认**：

| 选 | 做法 | 代价 |
|---|---|---|
| **A. 离场由玩家包做** | 订阅 `on_principal_logout`（D47）→ 把 `core:position` 存进本包 kv → `clear_position` | 多一套状态；**多端登录时一台退出会把化身弄下线**（`on_principal_logout` 是**凭据**被吊销时发的，别的设备可能还在线） |
| **B. 离线也站在原地** | 什么都不做 | 世界里有一具不动的身体（那是玩法选择，但不是"下线"） |

**② "候选的出生点"从哪来？**

今天是 `data/spawn.json` 里**一个**点（`_pick_tile`）。"候选**们**"要有来源：
包内数据列几个（简单，全世界共用），还是内容作者在地图上摆（`local:spawn` 之类的组件，
才能做到"每张图有自己的出生点"）。**这条没定，上线界面就只有一个真选项。**

**③ 流程跑完去哪？**

玩家包的视图如果**全是 `fullscreen`**，顶栏 tab 条就是**空的**（`App.vue:137` 只收
非 fullscreen）。创建完 / 上线完落脚到哪？目前只能落到另一个 fullscreen 视图（「我」）
或空态。**"看世界"的视图属于第二个包**（D48）——所以全新安装的体验会是
"人能站住、但没地方可看"。**这条要确认是否可接受。**

### 11.2 验收标准（实现时照这个测）

- 全新账号登录 → 落在**创建流程**，不是字母序第一个视图
- 创建完 → 能正常看到世界（或明确知道去哪儿）
- 已有化身的账号重登 → 落在**上线界面**，两个选项都真的生效
- 选"回到下线前位置" → 回到的就是下线时那一格（不是"地图某处"）
- 关掉页面再登录 → **仍然走上线界面**（不会重复创建）
