## 0. 一句话与三条边界

**一句话**：内核**不诞生角色、不指定落点、不标记"谁是玩家"**；它只保留"这次请求以哪个实体行动"这个指针，以及主体（账户）上下文与生命周期信号。**"玩家是什么"（一具化身 / 多具 / 没有 / 夺舍 / 共号）整个归玩法包。**

三条边界（这是本方案的立足点，改任何一条都要重新评估）：

| # | 边界 | 为什么不可动摇 |
|---|---|---|
| B1 | **行动实体指针留在内核** | D15 世界过滤（`play_active_for_entity`）、`/views` 过滤、SSE 订阅、`/scene`、G1/G12 感知、`api.caller()` 全读它。删掉它不是"更纯粹"，是这些治理能力一起失效 |
| B2 | **化身的诞生、落点、roster 归玩法包** | 这才是玩法：可能一具、可能多具、可能没有、可能有想不到的形式 |
| B3 | **内核不写任何"这是玩家"的标记** | `kind="player"` → `local:player` 是内核产出的虚构组件（D44 四象限里的 `fictional`），而 D42 早已判定"判断是不是人看账户绑定" |

**当前状态（本方案的清理对象）**：账号注册 → `IdentityService._materialize()`（`identity.py:475-498`）→ `place_entity("player", 首张图的 spawn_row/spawn_col, name=账号名, user_id=账户)`。实测：地图存在但出生格没有地块时，`POST /auth/register` 直接 **500**（`_register` 只捕获 `IdentityError`，`WorldError` 无人接）。

## 1. 需求（R1–R9）

| # | 需求 | 验收口径 |
|---|---|---|
| **R1** | **内核不存在"出生点"概念** | 代码/表结构/管理端/编辑器/内容/文档里不再有 `spawn_row` / `spawn_col` / `出生点`（CHANGELOG 历史条目除外） |
| **R2** | **内核不创建任何实体** | 注册、登录、agent 注册都不产生实体；`token.entity_id` 初始为空是合法状态 |

| **R4** | **roster（主体拥有哪些化身）完全归玩法包** | 内核只认"某一具当前行动的实体"，不持有列表 |

| **R7** | **内核提供主体生命周期信号** | 登录 / 登出 / 注销可被玩法包订阅，供"化身入场 / 离场 / 清理"使用（这是"只进不出"的解药） |

**非目标**：不做数据迁移（D13 无迁移，删库重建）；不把世界过滤/感知也下沉；不做会话管理 UI；不引入 ECS。

## 2. 职责切分

| 事实 | 归谁 | 存放 |
|---|---|---|
| 凭据（token）、账户、tier、principal | 内核 | `tokens` / `accounts` |
| **本次请求以哪个实体行动**（指针） | 内核记账，**写法由玩法包决定** | 当前 token 的 `entity_id`（建议，见 D-a） |
| **哪些实体是某主体的化身**（归属） | 内核记账，**写法由玩法包决定** | 实体上的 `core:account.user_id`（建议，见 D-b） |
| **roster：几具化身、怎么创建、怎么切换、落在哪** | **玩法包**（`play_data` KV + 自己的服务） | 包自己的 KV |
| 世界 / 地图 / 地块 / 位置组件 | 内核（数据与通道） | 现有表 |
| "玩家该不该出现在某地"这类规则 | 玩法包 | 包的组件 / KV |

**要点**：内核保留的是**两本账**（当前行动是谁 / 谁的化身有哪些），不是任何玩法决策。开这两本账的动作都由玩法包发起（窄口 API），内核不主动做任何事。

## 3. 依赖模型：玩家包是**软依赖锚点**，不是必经之路

用户设想是"其他包依赖一个单一的玩家包"。机制上 `requires.plays` 做得到，但它的真实语义必须先认清（已核实）：

- 依赖是**全局包级**的：加载时拓扑排序，**依赖未启用 → 依赖者直接加载失败**（`play/__init__.py:162-171`）；`enable` 会递归启用依赖；`disable` / `uninstall` 在有依赖者时**直接拒绝**（`:446-457`、`:496-497`）。
- 而**激活是世界级**的（D15），`call_service` **不做世界过滤**（`engine.py:1559-1566` 只查"服务存在 + 提供方已加载"）→ 某世界没启用玩家包，依赖者照样调得到它的服务（跨世界串味）。

因此按强度分三档，**推荐绝大多数包走零依赖**：

| 强度 | 写法 | 谁需要 |
|---|---|---|
| **零依赖**（默认） | `api.caller()` 直接拿当前行动的化身 | 移动、交互、战斗、背包……只关心"我现在是谁" |
| **软依赖** | `list_services()` 探测 + `call_service("<player>", "avatars_of" / "active_avatar" / "switch_to", …)` | 需要"我的**全部**化身"的包：队伍面板、切换角色、共号 UI |
| **硬依赖** | `requires.plays: ["<player>"]` | 仅"没有玩家包就没有意义"的包（如出生礼包要先有角色） |

**不推荐**让所有包硬依赖玩家包：那会重新造出 D31 想拆掉的东西（中心件 + 包间契约无系统表示，G39），并把玩家包变成单点故障（停它要先停所有依赖者）。

## 7. 已知的坑与交接提示

1. **`_entity_id()` 是硬闸**（`world/mcp/__init__.py:72-82`）：空值直接抛 `McpAuthError` → 工具回"连接未认证或凭据只能围观"（**文案误导**）。P1 必须先改这里，否则 R8 无从谈起。
2. **`/scene` 会 500**：`_build_scene` 要求 `require_position()`（`engine.py:3526`），而玩家端 app 只挂了 `HTTPException` 的处理（`http.py:567`）。P0 就要接。
3. **空实体的世界过滤会回落到默认世界**（`engine.py:2064-2076`）——合理降级，但必须写进文档，否则以后会被当 bug 查。
4. **`play_active_for_entity` 是视图过滤的唯一输入**（`http.py:461-466`）：无化身 + 非默认世界 = 入口消失（D-e）。
5. **`remove_entity` 不在原语分派表**：这是 D-b 选择"实体侧归属"的决定性理由。
